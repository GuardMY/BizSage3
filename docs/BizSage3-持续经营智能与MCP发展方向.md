# BizSage3 持续经营智能与 MCP 发展方向

## 1. 已确认的产品方向

BizSage3 将从一次性、对话式经营诊断助手，发展为面向企业老板和内部运营负责人的**持续经营智能与决策协同系统**。

产品不以复刻 Codex、Claude Code 一类通用执行 Agent 为目标。其竞争力应来自对企业实时经营状态的理解，以及将诊断建议转化为可审核、可追踪、可验证的业务闭环。

核心闭环如下：

```text
实时经营数据
  -> 异常与机会发现
  -> 归因分析与证据呈现
  -> 生成建议动作
  -> 人工审核
  -> 写回或触发业务系统动作
  -> 跟踪执行与经营结果
  -> 更新企业经营画像和后续策略
```

## 2. 产品定位与边界

### 产品定位

- 服务对象：企业老板和内部运营负责人。
- 核心问题：企业当前经营情况如何、发生了什么、为什么发生、下一步应做什么，以及行动后是否产生效果。
- 核心价值：把分散在 POS、ERP、CRM、财务、广告、电商和表格中的经营数据，转化为可解释、可执行、可复盘的运营决策。

### 不作为首要方向的能力

- 不建设无限制的通用工具市场或通用电脑操作 Agent。
- 不允许模型绕过人工审核，直接对外发送信息、修改经营数据或执行业务动作。
- 不以多 Agent 展示本身为目标；只有在角色分工能够提高诊断质量、审核效率或执行可靠性时才采用。

## 3. 当前基础

当前系统已具备向该方向演进的基础：

- 以 LangGraph 管理场景识别、事实采集、信息完备度和报告生成的有状态诊断流程。
- 已审核行业知识库、公开网络检索和服务端校验后的引用展示。
- 以 PostgreSQL、Redis 和后台任务支撑的会话、检查点和异步报告生成。
- 受限的只读工具调用、调用次数和超时控制，以及对工具返回内容的提示注入防护。

当前能力主要依赖用户在对话中描述经营事实，尚未形成与真实业务数据、业务动作和效果反馈相连的持续闭环。

## 4. MCP 的定位

MCP 是 BizSage3 接入外部系统和专业能力的受控协议层，不是独立的产品卖点。

MCP 接入必须经过 BizSage3 的租户、授权、数据口径、审批和审计边界。模型不应直接持有外部系统的高权限凭据，也不应直接调用具有写入副作用的工具。

```text
外部系统 / 数据源
  -> MCP Server
  -> BizSage3 集成网关
       - 租户与身份映射
       - 最小权限和凭据托管
       - 数据口径与模式校验
       - 调用配额、超时、重试和审计
  -> 经营数据层与诊断引擎
  -> 审批中心
  -> 执行型 MCP Server
  -> 外部业务系统
```

## 5. MCP 能力分层

### 5.1 读取型业务数据 MCP

目标是让诊断基于实时经营事实，而不只依赖人工口述。

- POS / 收银：交易、客单价、品类、门店、退款、时段。
- ERP / 供应链：库存、采购、缺货、履约、供应商。
- CRM：线索、商机、客户分层、复购、流失。
- 财务系统：收入、成本、毛利、现金流、应收应付。
- 广告投放平台：消耗、转化、获客成本、素材和渠道表现。
- 电商平台：流量、订单、转化率、评价、退货和履约。
- 表格与数据仓库：Excel / CSV、BI 数据集和企业已有数仓。

首期以只读授权为原则。读取结果须被标准化为带来源、时间范围、口径、刷新时间和数据质量状态的证据，而不是直接拼接进模型上下文。

### 5.2 分析与计算能力

分析能力应优先作为 BizSage3 内部的可测试服务实现；MCP 用于接入外部计算引擎或企业已有分析系统。

- 指标口径计算：同比、环比、结构占比、目标达成、漏斗转化。
- 异常发现：突增、突降、持续偏离、门店或渠道间异常差异。
- 归因分析：按时间、门店、渠道、品类、客户群和活动拆解。
- 经营测算：利润、现金流、库存周转、盈亏平衡、预算影响。
- 数据质量检查：缺失、延迟、口径冲突和异常值。

### 5.3 知识与外部事实 MCP

- 行业基准、政策、市场变化、竞品和公开研究资料。
- 企业内部 SOP、制度、目标、历史复盘和运营方法论。

所有知识型 MCP 返回内容均视为不可信资料。系统只将经检索、筛选和引用校验的内容作为证据；每条面向用户的事实性主张应能回溯到数据或资料来源。

### 5.4 执行型 MCP 与人工审批

执行型 MCP 用于将建议变为业务动作，但任何具有副作用的操作必须经过人工审核。

可支持的动作包括：

- 在项目或任务系统创建整改任务并指定负责人和截止时间。
- 向 CRM 写入跟进建议、待联系名单或标签草案。
- 生成广告调整、预算调整、促销或补货方案草案。
- 发送待审核的站内通知、邮件或协作消息。

执行流程必须是：

```text
建议动作 -> 展示影响范围、依据和风险 -> 审核人批准或驳回
-> 以审批快照执行 -> 记录外部系统回执 -> 可追踪、可撤销或补偿
```

模型只能提出动作和准备参数草案；审批服务代表用户发起最终写入。执行权限、金额阈值、可操作字段和审批人必须按租户及角色配置。

### 5.5 反馈型 MCP

反馈型 MCP 从任务和业务系统回收结果，形成长期经营记忆：

- 建议是否被采纳、由谁执行、是否逾期。
- 执行前后关键指标是否改善。
- 建议无效、条件变化或人工驳回的原因。
- 企业目标、约束和成功标准的变化。

这部分能力决定系统能否从“生成建议”升级为“持续改善经营结果”。

## 6. 演进原则

1. **先读后写**：先验证实时读取、口径统一和诊断效果，再扩展需要审批的写入动作。
2. **先证据后建议**：建议必须区分事实、推断、假设和推荐，并显示数据来源、时间范围和置信边界。
3. **最小权限**：每个 MCP Server、工具和令牌仅拥有完成当前任务所需的最小访问范围。
4. **审批不可绕过**：写入型动作由独立审批链路控制，不把“模型确认”当作用户授权。
5. **租户隔离与可审计**：数据访问、模型调用、审批、外部写入和回执都需要租户隔离和审计记录。
6. **可降级运行**：外部系统不可用、数据延迟或口径异常时，诊断应说明限制，不以过期或不完整数据伪造确定性结论。
7. **以业务结果评估**：评价指标不只看对话质量，还包括异常命中率、建议采纳率、执行完成率和目标指标改善情况。

## 7. 近期优先级

在不预设具体供应商的前提下，近期应按以下顺序验证：

1. 建立企业、数据源、指标口径、时间范围和数据质量的统一领域模型。
2. 接入一类高价值、可实时读取的数据源，验证“数据 -> 证据 -> 诊断”的完整链路。
3. 建立主动监测：异常事件、机会事件、诊断任务和人工确认。
4. 建立建议动作的审批中心和审计模型，再接入第一个低风险写入动作。
5. 接入执行结果与指标反馈，形成建议效果复盘。
6. 建立针对事实抽取、工具选择、归因质量、引用支撑和业务效果的评测体系。

## 8. 待决事项

以下事项需要在各阶段启动前单独确认，不应由本方向文档替代：

- 首批接入的业务系统、供应商和 API 可用性。
- 各数据源的授权方式、刷新频率、成本和数据保留规则。
- 企业指标口径、行业差异和数据质量标准。
- 审批角色、金额或风险阈值、撤销与补偿策略。
- 第一类允许写入的业务动作及其失败处理方式。
- 试点企业、成功指标和人工复核流程。
