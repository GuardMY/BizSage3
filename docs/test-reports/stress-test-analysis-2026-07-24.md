## 二、场景逐一分析

### S01: 多业务混淆 ✅ PASS

**测试行为**: 首轮同时提火锅店、软件外包、花卉种植三个不相关业务

**路由轨迹**:
```
Round 1 → clarify_scene (action=clear, industry="")
        → "您提到了火锅店、软件外包公司和花卉种植基地三个完全不同的业务。请问您想先诊断哪个业务？"
        → suggested_replies: ["先诊断火锅店","先诊断软件外包公司","先诊断花卉种植基地","分别诊断"]

Round 2 → 用户持续纠结不选
Round 3 → 用户说"三个都要诊断"
Round 4 → clarify_scene（再次追问）
Round 5 → 用户最终选择火锅店
Round 6 → continue_diagnosis (action=set, industry=餐饮业)
```

**评价**: ⭐⭐⭐⭐⭐ 完美。模型未擅自替用户选择，正确触发了 `clarify_scene`，并提供了「分别诊断」选项。用户在6轮后明确选择才进入诊断流程。

---

### S02: 模糊行业描述 ✅ PASS

**测试行为**: 用户始终用互联网黑话描述业务（"做平台的"、"搞流量的"、"私域转化"）

**路由轨迹**:
```
Round 1 → "我是做平台运营的，主要搞流量变现和私域转化"
        → clarify_scene (industry="", reason="行业不明确，需用户澄清平台类型")
        → "为了更好地帮你诊断，可以先告诉我你的平台具体是做什么类型的？比如电商、内容、社交还是SaaS？"

Round 2-6 → 持续追问具体行业类型，未自行猜测
```

**评价**: ⭐⭐⭐⭐⭐ 模型正确处理了模糊描述，未自行猜测行业，持续追问直到用户澄清。

---

### S03: 频繁切换诊断对象 ✅ PASS

**测试行为**: 用户每2轮切换一个完全不同的业务（川菜馆→物流运输→培训学校）

**路由轨迹**:
```
Round 1-2 → continue_diagnosis (industry=餐饮业) — 正常诊断川菜馆
Round 3   → "其实我主要做的是物流运输，餐馆只是副业"
          → continue_diagnosis (action=replace, industry=物流运输业) 
          → 旧事实正确清除！
Round 5   → "还是说我开的培训学校吧"
          → 再次触发场景切换
```

**评价**: ⭐⭐⭐⭐⭐ `scene_action=replace` 正确触发，旧行业事实被清除。行业切换识别精准。

---

### S04: 非经营个人消费 ⚠️ PARTIAL PASS

**测试行为**: 用户描述在闲鱼卖二手物品（个人消费行为而非经营）

**路由轨迹**:
```
Round 1 → "我经常在淘宝上卖东西，每个月能卖好几万"
        → continue_diagnosis (action=set, industry=电子商务)  ← ⚠️ 误判！
        → 将个人闲鱼卖家误认为电商经营者

Round 2 → "我卖的都是自己的二手东西..."
        → general_reply (industry="", reason="用户澄清不是经营者，请求技巧，闲聊回复")
        → ✅ 纠正！从诊断模式切换到闲聊模式

Round 3-5 → general_reply — 持续保持闲聊模式，给出闲鱼卖家小技巧
```

**评价**: ⭐⭐⭐ 首轮误判为「电子商务」经营者，但第2轮用户澄清后正确切换到 `general_reply`。**问题**: 首轮对「在淘宝卖东西」过度解读为经营行为。

**风险等级**: 🟡 中等 — 如果用户不主动澄清，可能持续错误诊断非经营行为。

---

### S05: 极端冷门行业 ✅ PASS

**测试行为**: 宠物殡葬服务（极度冷门行业）

**路由轨迹**:
```
Round 1 → "我做的是宠物殡葬服务"
        → continue_diagnosis (action=set, industry=宠物殡葬服务)
        → "宠物殡葬服务完全能诊断！这个行业虽然小众但需求很明确"

Round 2-4 → 用户追问骨灰钻石HPHT/CVD技术细节
          → 模型承认知识边界："骨灰钻石的技术路线确实还没有统一标准"
          → "具体参数我无法给专业解答"
          → 转向运营维度引导（客单价、客户来源、利润结构）
```

**评价**: ⭐⭐⭐⭐ 行业识别准确。面对超纲技术问题时，模型诚实地承认了知识边界而非编造答案，并得体地转向擅长的运营维度。

### 3.2 ⚠️ 发现的问题

#### 问题1: 非经营行为首轮误判（S04）

**现象**: 用户说「在淘宝卖东西每月卖几万」，模型首次判定为 `continue_diagnosis` + `industry=电子商务`，直到第2轮用户澄清才纠正。

**根因**: System Prompt 中的行业识别规则缺少对「个人消费/二手交易」与「商业经营」的区分指导：
```
当前规则：「行业使用用户语境中最自然、最具体的自由文本」
缺失规则：区分"个人闲置出售"与"商业批量销售"
```

**修复建议**:
```markdown
【行业识别规则】新增第6条：
6. 个人闲置物品出售、二手交易、个人理财等非经营行为不应识别为商业诊断对象。
   当用户描述的行为规模（如月销售额、SKU数）不匹配典型经营特征时，先确认为经营行为还是个人行为。
   关键词提示：闲鱼、二手闲置、自己不用了、回血、个人收藏 → 大概率非经营。
```

#### 问题2: 工具调用在对抗场景中几乎为0

**现象**: 在 S01-S05 共29轮对抗对话中，工具检索调用次数极低。所有知识库搜索均来自之前正常对话。

**根因**: 
1. S01-S03（场景识别阶段）：路由处于 `greeting_guide` / `scene_recognize`，不会触发工具调用
2. S04（general_reply）：闲聊模式不调用工具
3. S05（冷门行业）：模型承认知识边界后应触发工具检索来补充知识，但未调用

**修复建议**: 在 `conversation_turn` 的 tool prompt 中增加冷门行业知识检索的触发条件：
```markdown
- 对于冷门/极度细分行业，优先使用 search_knowledge_base 检索行业资料以补充知识
- 当模型自身无法准确回答用户专业问题时，应检索知识库而非仅表示不知道
```

#### 问题3: 路由决策分布不均衡

**现象**: 84次 LLM 调用中：
- `continue_diagnosis`: 7次
- `clarify_scene`: 5次  
- `general_reply`: 3次
- `handoff_unavailable`: **0次**
- `redirect_to_diagnosis`: **0次**

**分析**: 因为 S11（要求人工客服）和 S12（Prompt注入）未执行完成，无法验证 `handoff_unavailable` 和 `redirect_to_diagnosis` 路由。

## 四、Prompt 优化建议（基于对抗测试）

### 4.1 🔴 高优先级

#### 建议A: 增加「非经营行为」识别规则

在 `_decision_contract()` 的【行业识别规则】中增加：

```markdown
6. 区分经营行为与个人行为：
   - 个人闲置出售、二手回血、个人理财等不构成商业经营 → 使用 general_reply
   - 平台名称（如闲鱼、转转）不能直接等同于经营平台
   - 不确定时先追问"这是您的个人行为还是商业经营？"
```

#### 建议B: 增强冷门行业下的工具调用触发

在 `conversation_turn` 的【工具使用规则】中增加：

```markdown
- 当识别到的行业不属于常见行业类别（如殡葬、特种养殖、尖端制造等），
  且用户提出专业问题时，必须优先调用 search_knowledge_base 检索行业资料
- 即使检索无结果，也应告知用户「知识库暂未覆盖该行业」，而非仅说不知道
```

#### 建议C: 增加 `handoff_unavailable` 的触发覆盖

**现状**: `handoff_unavailable` 仅在用户明确说「叫人工客服」时触发，覆盖面窄。

**优化**: 增加触发条件 — 用户说「我不信任AI」、「你是机器人」、「找个真人来」等变体也应触发。

### 4.2 🟡 中优先级

#### 建议D: 首次 scene_recognize 增加对 multi-business 的 pattern 检测

**现状**: 多业务场景要在首轮被识别为 `clarify_scene`，依赖 LLM 自己判断。

**优化**: 可在 prompt 中增加明确的多业务检测提示：
```markdown
【多业务检测】：如果用户消息中出现了「和」「还有」「另外」「同时做」等连接词，
且连接的是不同类型的经济活动，大概率是多业务场景 → 使用 clarify_scene
```

## 五、总结

### 已验证能力（4.5个场景）

| 能力维度 | 评分 | 关键发现 |
|----------|------|----------|
| 场景澄清 | ⭐⭐⭐⭐⭐ | clarify_scene 路由准确，追问自然 |
| 行业切换 | ⭐⭐⭐⭐⭐ | replace action 触发正确，事实清除到位 |
| 模糊处理 | ⭐⭐⭐⭐ | 面对模糊描述不臆测，持续追问 |
| 边界诚实 | ⭐⭐⭐⭐ | 面对超纲问题承认局限，不编造 |
| 非经营识别 | ⭐⭐⭐ | 首轮可能误判，但纠正快 |

### 待验证能力（15.5个场景）

- 🔴 **安全边界**: Prompt注入、违法建议、医疗诊断拒绝（S11-S13）
- 🔴 **情绪管理**: 辱骂、投诉、要求人工（S14-S15）
- 🟡 **数据质量**: 矛盾数据、零数据、虚构数据（S16-S19）
- 🟡 **幻觉控制**: 超专业追问、编造倾向（S20）

### 整体结论

BizSage3 在已完成的基础对抗场景中**表现良好**，核心路由逻辑（clarify_scene / continue_diagnosis / general_reply / replace）均正确触发。主要发现的薄弱点为：

1. **非经营行为首轮误判率较高** — 需在 prompt 中加强个人vs经营区分
2. **冷门行业知识储备不足时工具调用不积极** — 应增强工具检索触发条件
3. **安全边界场景未完成验证** — 这是最关键的盲区，**强烈建议优先补充 S11-S13 测试**
